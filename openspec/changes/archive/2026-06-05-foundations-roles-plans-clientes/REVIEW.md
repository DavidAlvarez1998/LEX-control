## Verdict

Architecturally the proposal is well-aligned with the codebase idioms (catalog+override mirroring Servicio/EmpresaServicio, seeded catalogs like AreaPractica, errno-150 SetNull discipline, per-request DB role resolution) and is genuinely additive at the model level. The Cliente-vs-Litigante reconciliation (single-row lifecycle + nullable litiganteId bridge) is the right call. NOT yet safe to hand over as-is — fix the high-severity items first: (1) the migrate/rollback story is wrong for this push-managed DB (no migrations dir; `prisma migrate dev` risks a reset) — rewrite it or baseline first; (2) the seat gate's 'single chokepoint' is fictional — the existing /usuarios and /mi-empresa/usuarios endpoints create users and toggle esAdminEmpresa with no seat counting and no UsuarioRolEmpresa rows, so caps are bypassable and esAdminEmpresa/ADMINISTRADOR will drift. Also tighten: mandate empresaId comes only from req (never client input) in resolveEntitlements/seat-gate/requirePermiso; require same-empresa validation on Cliente's outgoing FKs; resolve the Modulo-vs-PlanFlag duplication for logo/ia; define cuotas for non-active subscriptions and fix the empty-rows FOR UPDATE race (lock the Suscripcion/Empresa row). Litigante upsert needs a real unique key or softened language. Confirm the 'ilimitado' reading for Bufete PRO and the precioEnSmmlv typing. Relevant files reviewed: /mnt/storage/DAVID/lex-control/lex-control-api/prisma/schema.prisma, /mnt/storage/DAVID/lex-control/lex-control-api/src/middleware/auth.ts, /mnt/storage/DAVID/lex-control/lex-control-api/src/modules/auth/auth.service.ts, /mnt/storage/DAVID/lex-control/lex-control-api/src/modules/usuarios/usuarios.router.ts, /mnt/storage/DAVID/lex-control/lex-control-api/src/modules/mi-empresa/mi-empresa.router.ts, /mnt/storage/DAVID/lex-control/lex-control-api/package.json (no prisma/migrations dir).

## Conflicts with current code (ordered)

### [HIGH] Migration/rollback narrative is false for this repo. There is NO prisma/migrations/ directory; the DB has been built with `prisma db push` (package.json has push; CLAUDE.md flags push as the prototyping path and memory shows db-push workflow). The proposal repeatedly promises a 'single prisma migrate dev' and a rollback via 'prisma migrate resolve/down to drop 12 tables and 6 enums'. With no migration baseline, `prisma migrate dev` will try to baseline/diff the ENTIRE existing schema (12+ existing tables) into an initial migration, and on a DB that already has those tables via push, migrate dev can prompt to RESET (data loss) or fail. The 'no destructive DDL' / 'down migration' rollback story does not apply to a push-managed DB.

**Fix:** Decide the DDL mechanism explicitly. Either (a) keep using `prisma db push` for this additive change and rewrite the proposal's migrate/rollback sections accordingly (rollback = manual DROP of the new tables/enums), or (b) first run `prisma migrate diff`/`migrate resolve --applied` to baseline the current schema into an initial migration on a non-prod copy, verify against the live DB, THEN add the foundations migration. Do not run `prisma migrate dev` against the live push-managed DB without baselining first.

### [HIGH] The proposal claims a 'single assignment chokepoint' for the seat gate, but no such chokepoint exists. Users are created/edited and esAdminEmpresa is toggled in at least three uncovered write paths today: usuarios.router.ts POST / and PATCH /:id (admin), and mi-empresa.router.ts POST /usuarios and the activation/deactivation handlers. None of these create UsuarioRolEmpresa rows or pass through resolveEntitlements. So after foundations, creating a member via the existing flows yields a user with zero RolEmpresa rows (req.rolesEmpresa = []) and no seat consumed, while the new seat gate only guards a hypothetical future endpoint.

**Fix:** Spec the integration with the EXISTING user-management endpoints, not just a new one. Either route esAdminEmpresa toggles and member creation through the seat-gated role-assignment path (so ADMINISTRADOR mirror + seat counting actually happen), or explicitly scope-out and document that existing endpoints bypass the seat gate (and accept the drift). As written the seat cap is trivially bypassable via the current /usuarios and /mi-empresa/usuarios routes.

### [MED] esAdminEmpresa vs RolEmpresa.ADMINISTRADOR is a dual source of truth that WILL drift through existing code. mi-empresa POST /usuarios and usuarios PATCH set esAdminEmpresa directly with no RolEmpresa side-effect. The proposal says 'keep esAdminEmpresa in sync on assignment of ADMINISTRADOR' but the existing flows set the flag WITHOUT an assignment, so a user can be esAdminEmpresa=true with no ADMINISTRADOR row, or vice-versa. The proposal's own requirePermiso spec makes esAdminEmpresa short-circuit RBAC, so the flag is security-load-bearing yet unsynced.

**Fix:** Define the sync as bidirectional and enforce it at every flag-write site (the two routers), or make ADMINISTRADOR derived from esAdminEmpresa (don't store it as a separate seat row), or make esAdminEmpresa derived from holding ADMINISTRADOR. Pick one authoritative source and remove the other as independently writable.

### [MED] Litigante has NO unique constraint on (empresaId, tipoDocumento, numeroDocumento) in the current schema, and tipoDocumento/numeroDocumento are both nullable. The clientes spec says conversion MUST 'upsert/link a Litigante matched on (empresaId, tipoDocumento, numeroDocumento)'. A Prisma upsert requires a unique key on those columns; without it the 'upsert' is a non-atomic find-or-create that can create duplicate Litigantes under concurrency, and nullable document fields make the match key unreliable for leads with no documento.

**Fix:** If atomic match-on-document is a requirement, add @@unique([empresaId, tipoDocumento, numeroDocumento]) to Litigante (note: nullable columns mean NULLs are distinct in MySQL, so leads without docs won't collide — acceptable but document it). Otherwise downgrade the spec language from 'upsert' to 'application-level find-or-create, best-effort, may duplicate' and handle dedupe explicitly. Adding the unique constraint is itself a schema change to an existing table the proposal claims it does not touch.

### [MED] PlanFlag (string flag) and Modulo overlap as two mechanisms for the same toggles. logo_personalizado and ia_redaccion appear BOTH as non-baseline Modulo claves (empresa-roles spec) AND as PlanFlag strings (planes-entitlements spec). This is a third source of truth: is logo_personalizado entitlement checked via modulosHabilitados or via plan_flags? resolveEntitlements only returns {modulosHabilitados, cuotas} — flags are not in its output, so anything gated by a flag has no resolver path.

**Fix:** Pick one representation. Either model logo_personalizado/ia_redaccion/automatizacion_contratos purely as non-baseline Modulos (drop PlanFlag), or keep PlanFlag and have resolveEntitlements also return a flags map and define which features read flags vs modules. As written, two of the eleven 'modules' duplicate three of the flags with no defined precedence.

### [MED] NULL-as-Infinity seat cap interacts dangerously with the FOR UPDATE seat gate, and the 'no active suscripcion => only baseline' policy can lock companies out. (1) If a Suscripcion is SUSPENDIDA/CANCELADA, resolveEntitlements grants only baseline modules and presumably zero non-baseline cuotas; the spec does not define cuotas for a non-active subscription, so seat assignment for JURIDICO could compare against undefined/0 and reject ALL assignments for a suspended firm — including re-enabling. (2) The seat gate locks 'the empresa's usuario_roles_empresa rows' but a brand-new role (e.g. first CONTABLE, zero existing rows) has no rows to lock, so FOR UPDATE locks nothing and two concurrent first-CONTABLE inserts can both pass.

**Fix:** Define cuotas explicitly for non-active subscriptions (e.g. all caps 0, or retain plan caps but block writes). For the empty-rows race, lock a stable parent row instead — SELECT ... FOR UPDATE on the Suscripcion (or Empresa) row, or use an INSERT against a unique seat-slot table / serializable transaction — so the lock exists even when the role currently has zero assignments.

### [LOW] precioEnSmmlv Decimal(10,2) is mis-modeled for the 'Bufete PRO = 1 SMMLV' case. SMMLV is a multiplier/index (~1.00), not a peso amount; storing it as Decimal(10,2) alongside a REQUIRED precioMensual Decimal(10,2) forces a frozen COP value for a plan whose whole point is to track the minimum wage. The seed scenario says precioMensual is non-null for all five plans, which contradicts 'resolved at billing time' for bufete_pro.

**Fix:** Make precioMensual nullable (NULL for bufete_pro, with precioEnSmmlv carrying the multiplier), or rename precioEnSmmlv to a clearer multiplier field and document that COP = multiplier * SMMLV resolved by the contable module. Clarify the seed so bufete_pro does not store a stale frozen peso price.

## Gaps vs the docs

- Roles vocabulary gap: docs imply role 'jurídico' = abogado and the bridge requires assigning a proceso to 'an abogado'. RolEmpresa has JURIDICO but Tramite.responsableId is a plain Usuario FK with no constraint that the responsable holds JURIDICO. The proposal only adds the app-suggestion that responsableComercial SHOULD hold COMERCIAL; it says nothing about responsable/abogado SHOULD hold JURIDICO. The 'Solicitud de Asignación' bridge target (assign proceso to an abogado) is left without even an app-level role expectation.
- necesidadTipoProceso values gap: the docs enumerate specific 'necesidad del proceso' options (derecho de petición, acción de tutela, acción popular, reclamación administrativa, conciliación extrajudicial, proceso sancionatorio ambiental, procesos judiciales). The proposal wires necesidadTipoProcesoId -> TipoProceso (good, reuses catalog) but does not confirm these specific TipoProceso rows are seeded/available, so a prospecto's stated need may have no selectable type at CRM time. Verify the legal-tramites seed covers these or document the gap.
- Plan quota for COMERCIAL on base 'independiente' and admin count nuance: docs say Independiente = 1 jurídico + 1 admin only (no comercial, no contable). Spec matches. But docs Bufete PRO = 'usuarios ILIMITADOS, 2 admins' — spec sets ADMINISTRADOR:2 and others NULL. Confirm 'ilimitado' is intended to apply to ADMINISTRADOR too or is genuinely capped at 2; the docs phrase 'usuarios ilimitados' could be read as all roles unlimited. This is a load-bearing ambiguity for the highest tier.
- Module enablement for 'export_excel' as baseline: docs list 'export Excel' under the BASE Independiente plan's module bundle, which the proposal treats as baseline (always-on for everyone). That is a reasonable reading but means even a hypothetically lower/free tier gets export — confirm no tier should lack it. Minor, but it's a policy decision folded silently into esBaseline.
- Cliente lifecycle write-authority gap: spec says PROSPECTO->CLIENTE (convertidoEn) is written by the contratos module 'when contrato + poder firmado' — but contratos is out of scope and not yet built. Foundations provides columns but there is no defined interim mechanism to convert, and DESCARTADO/back-transitions (e.g. CLIENTE reverting, or re-activating a DESCARTADO lead) are unspecified. The lifecycle state machine's allowed transitions are not pinned down.
- Cliente has no document uniqueness or dedupe within empresa: a despacho could create many Cliente rows for the same person (no @@unique on documento), which then each try to link/upsert the same Litigante on conversion. Dedup policy for Cliente itself (not just Litigante) is missing.
- No spec for what happens to req.rolesEmpresa for platform ADMIN (empresaId null). requireAuth will run the new resolution for ADMIN too; UsuarioRolEmpresa requires empresaId, so ADMIN has none — fine, empty array — but requirePermiso is presumably never mounted on ADMIN endpoints. Confirm platform ADMIN is explicitly out of the empresa-roles axis so an ADMIN hitting an empresa-scoped permiso endpoint gets a clean 400/403, not an undefined-empresaId crash in resolveEntitlements.

## Multi-tenant / privilege-escalation checks

Mostly sound but with concrete gaps. Positives: UsuarioRolEmpresa denormalizes empresaId and indexes [empresaId, rolEmpresa]; Cliente is empresaId-scoped with cross-tenant isolation scenarios; resolveEntitlements is keyed by empresaId; Suscripcion is @@unique([empresaId]). The existing tenant pattern (updateMany filtered by empresaId, e.g. mi-empresa router) is the right precedent and the new models follow it.

Risks: (1) The seat gate and requirePermiso must derive empresaId from req (DB-resolved) and NEVER from client input; the specs assume resolveEntitlements(empresaId) but do not state the empresaId source is the authenticated req.empresaId. If any new endpoint accepts empresaId from the body/params, a USUARIO could resolve another tenant's entitlements or assign roles cross-tenant. Must mandate empresaIdRequerido(req) as the only source.

(2) Privilege-escalation via esAdminEmpresa short-circuit: requirePermiso lets esAdminEmpresa=true bypass the RBAC gate for ANY permiso in a contracted module. Since esAdminEmpresa is set by the existing /usuarios and /mi-empresa routes without any RolEmpresa/seat linkage, an empresa admin effectively holds every permiso of every contracted module regardless of seat caps — that's by design, but it means CONTABLE/COMERCIAL seat caps do not actually limit who can perform those modules' actions (the admin can do them all). Confirm this is acceptable; otherwise the seat quotas are cosmetic for admins.

(3) responsableComercialId / necesidadTipoProcesoId / litiganteId on Cliente are SetNull FKs to Usuario/TipoProceso/Litigante. Nothing in the spec enforces that the referenced Usuario or Litigante belongs to the SAME empresa as the Cliente. Application code must validate same-empresa on write or a despacho could point responsableComercialId at another tenant's Usuario id (cross-tenant reference leak). The 'SHOULD hold COMERCIAL' check is mentioned but same-tenant validation is not.

(4) No cross-tenant leak in the catalogs themselves (Modulo/Permiso/RolEmpresaPermiso are global, correct). Good.

## Open questions to confirm (from synthesis)

- RolEmpresa as a closed enum {ADMINISTRADOR, JURIDICO, CONTABLE, COMERCIAL} vs a per-empresa custom-role table: the docs only require these 4 quota slots, so foundations uses the enum. Confirm you do NOT need despachos to define custom-named roles (e.g. 'Abogado Senior') in this phase — if you do, RolEmpresa must become a table now (Lens 2's model) rather than a later migration.
- Cliente/Prospecto as ONE row with an estado lifecycle (recommended: preserves lead history, single bridge anchor) vs two tables (Prospecto that promotes into Litigante). Confirm the single-row model is acceptable.
- Seat-counting semantics: a seat is consumed by a UsuarioRolEmpresa row and is freed ONLY by removing that role (NOT by deactivating the user with activo=false). Confirm — alternative is to count only assignments whose Usuario.activo=true (one-line COUNT predicate change), which would let deactivation free seats. Decide before build.
- esAdminEmpresa vs RolEmpresa.ADMINISTRADOR: recommendation keeps esAdminEmpresa authoritative for team management (requireEmpresaAdmin unchanged) and treats ADMINISTRADOR as its synced module-layer mirror. Confirm, or decide to make ADMINISTRADOR authoritative and deprecate esAdminEmpresa (bigger migration, touches existing gate).
- Default grandfathered Plan for existing empresas on backfill (proposed: Firma, since the live product is the procesos/legal module). Confirm which plan, and whether a 'no Suscripcion' empresa should default to baseline-módulos-only-with-no-caps or be blocked.
- Bufete PRO price 'en SMMLV': store precioEnSmmlv (indexed to legal min wage, resolved at billing time) vs freezing a COP amount in precioMensual. Confirm the SMMLV-indexed approach and who provides the current SMMLV value to the contable module.
- Permiso granularity for seeding: confirm the initial permission claves / action vocabulary (crear/ver/editar/eliminar/asignar/exportar) per módulo, or defer the full catalog to each module's own change and seed only a minimal foundations set now (e.g. usuarios.*, cliente.*).
- Should baseline módulos (reportes/calendario/notificaciones/judicial/extrajudicial/export_excel) be seeded as explicit PlanModulo rows on every plan, or treated as always-on in code via Modulo.esBaseline (recommended)? Confirm to avoid double source-of-truth.
