# Proposal: Contable — Income/Expense Ledgers, Bolsas, and the Cartera Saldo-Resolution Loop

## Intent
The `contable` módulo (already a seeded non-baseline `Modulo`, contracted by the `independiente_pro`/`firma`/`bufete`/`bufete_pro` plans, with the `RolEmpresa.CONTABLE` axis already on the RBAC matrix) needs its data layer: per-empresa ledgers of actual money received (`Ingreso`) and paid out (`Egreso`), the typed operational-expense tables (`Nomina`, `CajaMenor`/`CajaMenorMovimiento`, `ServicioFijo`), the bolsas bancarias (`CuentaBancaria`) money lives in, a thin `Cartera` head that finally RESOLVES the `saldoPendiente` comercial left as a serializer placeholder, and the derived monthly `reportes`. This change introduces those layers **additively** on top of the foundations + comercial spines — `Cliente` and `Proceso` are reused as anchors and `ConfiguracionCobro`/`ContratoComercial` are READ (never rewritten) — so a despacho's CONTABLE/ADMINISTRADOR users can record cash flow, derive bolsa balances and cartera, and produce a monthly P&L without contable ever owning a billing engine or a scheduler.

## Background / Current State
Foundations (`foundations-roles-plans-clientes`) already shipped the `contable` `Modulo` (`esBaseline=false`, contracted by the paid plans), the `RolEmpresa` axis including `CONTABLE`, the entitlement módulo gate (`requirePermiso` raises 403 "Módulo no contratado" when the módulo is not contracted; `esAdminEmpresa` does NOT bypass it), and the seed idiom this change mirrors: a typed array → `PERMISOS.push({ ..., modulo })` + an RBAC loop with a `soloAdmin` flag (exactly the existing `COMERCIAL` array). Comercial (`comercial-funnel`, APPLIED + archived) shipped `ContratoComercial` (`contratos_comerciales`), the authoritative 1:1 `ConfiguracionCobro` plan (`configuraciones_cobro`, `contratoId @unique`, fields `modalidadCobro`/`valorFijo`/`porcentajeExito`/`numeroCuotas`/`valorCuota`/`fechaPrimerPago`), the closed shared `ModalidadCobro { CUOTALITIS, CUOTA_MIXTA, PRIMA_EXITO, FIJO, OTRO }` enum, and EXPLICITLY left `saldoPendiente` as a derived serializer placeholder (comercial-alertas: "MUST be computed in the read/serializer layer and MUST NEVER be persisted"). Legal (`legal-tramites`) owns `Proceso` (`tramites`, `radicado?` 23-digit nullable, `@@unique([empresaId, codigoInterno])`) and `Cliente` is the foundations CRM anchor (`clientes`, Cascade from `Empresa`). The `clientes.router.ts`/`comercial.router.ts` establish the exact tenancy idiom: `empresaId` always from the token via `empresaIdRequerido(req)`, a hard `WHERE { empresaId }` on every query, and app-level `assertSameEmpresa` on every outgoing FK (Prisma FKs do not prevent cross-tenant links).

What does NOT exist yet: any way to record actual money received or paid, payroll, petty cash, recurring fixed bills, bolsas bancarias, a cartera that turns the comercial cobro PLAN into a real saldo, or a monthly P&L. This change adds exactly those, reusing `Cliente`/`Proceso` as anchors (no copy, no redefinition) and mirroring the satellite/errno-150 idiom (denormalized `empresaId` plain column with NO FK, exactly ONE Cascade root per table, every other ref a scalar app-validated by `assertSameEmpresa`).

**DDL reality:** this repo manages MySQL with `prisma db push` — there is no `prisma/migrations/` directory. This change is applied additively with `prisma db push` + `pnpm generate`, NOT `prisma migrate dev` (which would try to baseline the entire push-managed schema and can prompt a destructive reset).

## Scope

### In Scope
- **Ingresos ledger (`contable-ingresos`)** — append-only `Ingreso` (`@@map("ingresos")`): actual money RECEIVED, the input that RESOLVES comercial's `saldoPendiente`. `clienteId` FK→`Cliente` (Cascade — the SOLE FK / cascade root); scalar `procesoId?`/`contratoId?`/`configuracionCobroId?`/`cuentaId?`/`registradoPorId?` (NO Prisma FK; app-validated same-empresa); `radicado?` snapshot of `Proceso.radicado`; `valorRecibido Decimal(14,2)`; `tipoCobro TipoCobroIngreso`; `metodoPago MetodoPago`; `estadoPago EstadoPagoIngreso @default(PAGADO)`; `soportePagoUrl?`. Indexes `@@index([empresaId, fechaIngreso])`, `@@index([clienteId])`, `@@index([empresaId, procesoId])`, `@@index([empresaId, radicado])`, `@@index([configuracionCobroId])`, `@@index([empresaId, estadoPago])`.
- **Egresos ledger (`contable-egresos`)** — append-only `Egreso` (`@@map("egresos")`): money PAID OUT, `GENERAL` overhead OR `POR_PROCESO` costs/costas. Tenant-scoped leaf (no Cascade FK — `GENERAL` has no cliente); `empresaId` denormalized + ALL refs scalar; `valorGasto Decimal(14,2)`; `categoriaGasto CategoriaEgreso`; `medioPago MetodoPago`; `estadoGasto EstadoGastoEgreso @default(PAGADO)`; `soporteGastoUrl?`. Doctrine: Egreso holds ONLY `GENERAL` + `POR_PROCESO` costs NOT already represented in `Nomina`/`CajaMenor`/`ServicioFijo` (no settling-Egreso emission). Indexes `@@index([empresaId, fechaGasto])`, `@@index([empresaId, categoriaGasto])`, `@@index([empresaId, radicado])`, `@@index([empresaId, procesoId])`.
- **Nómina (`contable-nomina`)** — per-period `Nomina` (`@@map("nominas")`): tenant-scoped leaf; scalar `empleadoId?` (NO FK; MAY point at `Usuario.id` today, future `Empleado.id` later) + REQUIRED `nombreEmpleado` snapshot + `cargo?`/`tipoVinculacion`; `periodo` String `'YYYY-MM'`; `valorNetoPagar Decimal(14,2)` (frozen COP, NO SMMLV indexing) plus `salarioHonorarios`/`auxilioTransporte?`/`bonificaciones?`/`descuentos?` all `Decimal(14,2)`; `estadoPago EstadoPagoNomina @default(PENDIENTE)`; scalar `cuentaId?`; `comprobantePagoUrl?`. Indexes `@@index([empresaId, periodo])`, `@@index([empresaId, empleadoId])`.
- **Caja menor (`contable-cajamenor`)** — `CajaMenor` (`@@map("cajas_menores")`) petty-cash fund header (Cascade root for its movements) with `montoInicial Decimal(14,2)`, `estado EstadoCajaMenor @default(ACTIVA)`, scalar `responsableId?`; and `CajaMenorMovimiento` (`@@map("caja_menor_movimientos")`) the ONE satellite-of-satellite: `cajaId` FK→`CajaMenor` (Cascade — SOLE FK), `tipoMovimiento TipoMovCaja @default(SALIDA)`, `categoria CategoriaCajaMenor`, `valor Decimal(14,2)`, `medioSalida MetodoPago`, scalar `procesoId?`/`responsableId?`, `radicado?`, `soporteUrl?`. `saldoActual`/`saldoRestante` DERIVED, never stored. Indexes `@@index([empresaId])` (header), `@@index([cajaId, fechaMovimiento])` + `@@index([empresaId])` (movements).
- **Servicios fijos (`contable-serviciosfijos`)** — `ServicioFijo` (`@@map("servicios_fijos")`) recurring fixed bills per period: tenant-scoped leaf; `periodo` `'YYYY-MM'`; `tipoServicio TipoServicioFijo`; `proveedor`; `valorFacturado Decimal(14,2)`; `fechaVencimiento?`/`fechaPago?`; `estadoPago EstadoServicioFijo @default(PENDIENTE)` (`VENCIDO` also derivable from `fechaVencimiento < now`); scalar `cuentaId?`; `soporteFacturaUrl?`. `@@unique([empresaId, tipoServicio, proveedor, periodo])`; indexes `@@index([empresaId, periodo])`, `@@index([empresaId, estadoPago, fechaVencimiento])`.
- **Cuentas / bolsas (`contable-cuentas`)** — `CuentaBancaria` (`@@map("cuentas_bancarias")`): tenant-scoped leaf bolsa; stores ONLY `saldoInicial Decimal(14,2) @default(0)`; `tipoCuenta TipoCuentaBancaria`; `estadoCuenta EstadoCuentaBancaria @default(ACTIVA)` (`CONCILIACION_PENDIENTE` is a manual flag); scalar `responsableId?`. Referenced by scalar `cuentaId` on `Ingreso`/`Egreso`/`Nomina`/`ServicioFijo`. `saldoActual` DERIVED. App blocks delete if any movement references it (Servicio `onDelete: Restrict` spirit). Indexes `@@index([empresaId])`, `@@index([empresaId, estadoCuenta])`.
- **Cartera (`contable-cartera`)** — THIN head `Cartera` (`@@map("cartera")`) per cobro plan that RESOLVES the comercial saldo: `clienteId` FK→`Cliente` (Cascade — SOLE FK); scalar `procesoId?`; `contratoId? @unique` + `configuracionCobroId? @unique` (ONE Cartera per contract/plan); `valorTotalAcordado Decimal(14,2)?` SNAPSHOT from `ConfiguracionCobro` at cartera-open; `tipoCobro ModalidadCobro` (REUSE comercial enum, denormalized for display); `fechaProximoPago?`; `estadoCartera EstadoCartera @default(AL_DIA)` (the one maintained label — recomputed on `Ingreso` write, indexable for vencido alerts); scalar `responsableId?`. `valorPagado`/`saldoPendiente` are DERIVED, NEVER stored. Indexes `@@unique([contratoId])`, `@@unique([configuracionCobroId])`, `@@index([empresaId, estadoCartera])`, `@@index([clienteId])`, `@@index([empresaId, fechaProximoPago])`.
- **Reportes (`contable-reportes`)** — `GET /contable/reportes?periodo=YYYY-MM`: fully DERIVED monthly P&L (no stored rows, no scheduler), one Prisma aggregate/groupBy per block. `totalIngresosMes`, `totalEgresosMes` (the 4 source tables — Egreso/Nomina/CajaMenorMovimiento/ServicioFijo — summed SEPARATELY to avoid double-counting), `utilidadNeta`, `totalGastosProceso` (groupBy `procesoId`, `radicado` display-only), plus cartera/caja-menor/servicios-fijos/bolsas blocks. Gated by `contable.reporte.ver` (soloAdmin).
- **Enums** — 17 new additive enums (listed in Capabilities); `ModalidadCobro` is REUSED from comercial (NOT redefined). `MetodoPago` is shared by `Ingreso.metodoPago`/`Egreso.medioPago`/`CajaMenorMovimiento.medioSalida`.
- **Permisos** — seeded idempotently in `seed-foundations.ts` via a NEW `CONTABLE` array → `PERMISOS.push({ modulo: "contable" })` + RBAC loop (mirrors the existing `COMERCIAL` array). Concrete claves, NO wildcards. RBAC `[ADMINISTRADOR, CONTABLE]` EXCEPT `contable.reporte.ver`/`contable.cartera.ver`(gestión)/`contable.cuenta.*`(config) → `[ADMINISTRADOR]` (`soloAdmin: true`).
- **Schema apply** — single `prisma db push` + `pnpm generate`: 17 new enums, 8 new tables, virtual back-relations on `Cliente`/`CajaMenor`. No backfill (all tables start empty; first row is lazy).

### Out of Scope
- A real billing/dunning engine: contable RESOLVES `saldoPendiente` by DERIVING it from the `Ingreso` ledger + the snapshotted `Cartera.valorTotalAcordado`; it does NOT generate cuotas, recibos, mora accrual, or interest.
- Any WRITE into the comercial módulo — `ConfiguracionCobro`/`ContratoComercial` are READ-only join sources; the existing comercial serializer may backfill its `saldoPendiente` placeholder via a shared contable helper or `GET /contable/cartera`.
- A scheduler/cron — every balance, total, saldo, and the `VENCIDO`/aging heuristics are derived at read-time.
- Document upload/storage infrastructure — only inline `soporte*Url String?` columns (URLs only); the polymorphic `DocumentoContable` table is a RESERVED name only (Q9), not built.
- A contable `Empleado`/HR entity — payroll uses a scalar `empleadoId` + snapshot (Q2); the future `contratos` (HR) módulo will own a rich `Empleado`.
- Excel/PDF export of reports (the `export_excel` módulo is a flag only).
- Any change to the BEHAVIOR or columns of `Cliente`, `Proceso`, `ConfiguracionCobro`, `ContratoComercial`, or existing auth gates (only additive virtual back-relations).

## Capabilities

### New Capabilities
- `contable-ingresos`: append-only `Ingreso` ledger of actual money received; `clienteId` SOLE Cascade root; the input that resolves comercial's `saldoPendiente`.
- `contable-egresos`: append-only `Egreso` ledger of money paid out (`GENERAL`/`POR_PROCESO`); tenant-scoped leaf; holds only costs not covered by the typed expense tables.
- `contable-nomina`: per-period `Nomina` with a scalar `empleadoId` + required snapshot (no `Empleado` entity); tenant-scoped leaf.
- `contable-cajamenor`: `CajaMenor` fund header (Cascade root) + `CajaMenorMovimiento` (cajaId Cascade — the one satellite-of-satellite); derived running balance.
- `contable-serviciosfijos`: `ServicioFijo` recurring fixed bills per period; `@@unique([empresaId, tipoServicio, proveedor, periodo])`; vencimiento heuristic.
- `contable-cuentas`: `CuentaBancaria` bolsas; stores only `saldoInicial`, derives `saldoActual`; referenced by scalar `cuentaId` everywhere; delete blocked while referenced.
- `contable-cartera`: thin `Cartera` head per cobro plan; snapshots `valorTotalAcordado` from comercial, derives `valorPagado`/`saldoPendiente`, maintains the indexable `estadoCartera` label.
- `contable-reportes`: derived monthly P&L (`GET /contable/reportes`) with the 4-table separate-sum doctrine; no stored rows, no scheduler.

### Modified Capabilities
- `clientes`: *extended* — `Cliente` gains virtual back-relations (`ingresos`, `cartera`); no column or enum change. `Cliente` is reused as the Cascade root for `Ingreso` and `Cartera`.
- `comercial-contrato-cobro`: *extended (read-only)* — no schema change; `ConfiguracionCobro`/`ContratoComercial` are READ as the cartera saldo-resolution join source. The comercial serializer's `saldoPendiente` placeholder MAY be backfilled by a shared contable helper. No column/enum change; `ModalidadCobro` is reused, not modified.

## Approach
Reuse `Cliente` and `Proceso` as anchors and never redefine them: every contable table carries a denormalized `empresaId` plain indexed column with NO FK, exactly ONE Cascade root (`Ingreso`→`Cliente`, `Cartera`→`Cliente`, `CajaMenorMovimiento`→`CajaMenor`; the remaining tables — `Egreso`/`Nomina`/`ServicioFijo`/`CuentaBancaria`/`CajaMenor` — are tenant-scoped leaves with NO Cascade FK), and every other reference (`procesoId`, `clienteId` where not the root, `cuentaId`, `empleadoId`, `responsableId`, `registradoPorId`, `contratoId`, `configuracionCobroId`) is a SCALAR with NO Prisma FK, app-validated same-empresa via `assertSameEmpresa` on CREATE/PATCH — exactly the foundations/comercial errno-150 discipline. The DERIVE doctrine is absolute (matching comercial-alertas + the `saldoPendiente` placeholder): balances (`saldoActual`, `saldoRestante`), totals (`totalIngresosMes`, `utilidadNeta`), and `valorPagado`/`saldoPendiente` are computed in the read/serializer layer and NEVER persisted — no stored running balances (no race conditions, no recompute jobs), no scheduler. Cartera is a THIN head: it snapshots `valorTotalAcordado` from `ConfiguracionCobro` at open (mirroring the comercial `cobroSnapshot` immutability idiom, so later plan edits don't silently move the agreed total), keeps the ONE maintained label `estadoCartera` (a derived label, not money — recomputed on `Ingreso` write inside the same request for an indexable vencido-alert filter), and derives all money. The 4 source expense tables are INDEPENDENT and summed SEPARATELY in the monthly report with NO settling-Egreso emission (Egreso holds only costs not already in a typed table) — a single documented doctrine that dodges double-counting. **The one critical coupling point is read-only**: contable becomes AUTHORITATIVE for `saldoPendiente` by JOINING comercial (`ConfiguracionCobro.contratoId → ContratoComercial.clienteId`; `Ingreso.clienteId` + optional `configuracionCobroId`) — it READS comercial and NEVER writes into it. Tenancy is enforced exactly like `clientes.router.ts`: `empresaId` from the token, hard `WHERE { empresaId }`, `assertSameEmpresa` on every scalar FK, a CONCRETE `requirePermiso("contable.*")` on every endpoint; the módulo gate (`contable` `esBaseline=false` → 403 "Módulo no contratado") is already in place and `esAdminEmpresa` does NOT bypass it. Everything is additive via `prisma db push`.

## Risks
| Risk | Likelihood | Mitigation |
|------|------------|------------|
| MySQL errno-150 (multiple cascade paths to one table) | Med | Exactly ONE Cascade FK per table: `Ingreso`→`Cliente`, `Cartera`→`Cliente`, `CajaMenorMovimiento`→`CajaMenor`; the other 5 tables are tenant-scoped leaves with NO Cascade FK; every cross-table ref (`procesoId`/`cuentaId`/`contratoId`/`configuracionCobroId`/`empleadoId`/`responsableId`/`registradoPorId`) is a SCALAR with NO Prisma FK |
| Cross-tenant scalar FK via a request body (`cuentaId`, `procesoId`, `contratoId`, `configuracionCobroId`, `clienteId`) | Med | `empresaId` only from `req`; `assertSameEmpresa` on every outgoing scalar FK on CREATE/PATCH; `Ingreso.clienteId` validated same-empresa on write so cartera `valorPagado` cannot leak across tenants |
| Snapshot drift: `Cartera.valorTotalAcordado` diverges from an edited `ConfiguracionCobro` | Low (intended) | `valorTotalAcordado` is intentionally frozen at cartera-open (mirrors comercial `cobroSnapshot`); an explicit re-sync action re-reads the plan; later plan edits never silently move the agreed total |
| Double-counting expenses in `totalEgresosMes` | Med | Single documented doctrine: the 4 source tables (`Egreso` GENERAL/POR_PROCESO, `Nomina`, `CajaMenorMovimiento`, `ServicioFijo`) are INDEPENDENT and summed SEPARATELY; Egreso holds ONLY costs not already in a typed table; NO settling-Egreso emission (rejected — adds a write-coupling double-count trap for zero benefit in a derive-only model) |
| Stored running balance race (two concurrent movements) | N/A (avoided) | No running balances stored: `saldoActual`/`saldoRestante` are DERIVED from `montoInicial`/`saldoInicial` + sums at read-time |
| `estadoCartera` label drifts from derived money | Low | `estadoCartera` is the ONLY maintained column and is a derived LABEL (not money): recomputed from `valorPagado`/`saldoPendiente`/`fechaProximoPago` on every `Ingreso` write in the same request; money itself is always re-derived on read |
| `cuotaInicial`/`VENCIDO`/aging alert fires without true payment data | Low (provisional) | Documented as `fechaVencimiento < now` / `fechaProximoPago < now` date-passed heuristics; PRIMA_EXITO/contingent totals report `saldoPendiente` as `null`/'indeterminado' and are excluded from al_dia/vencido aggregation |
| Deleting a `CuentaBancaria` orphans `cuentaId` references | Med | App blocks delete when any `Ingreso`/`Egreso`/`Nomina`/`ServicioFijo`/movimiento references it (Servicio `onDelete: Restrict` spirit); `CONCILIACION_PENDIENTE`/`INACTIVA` are the soft-disable path |
| Contable accidentally writes into comercial | Low | Hard boundary: `ConfiguracionCobro`/`ContratoComercial` are READ-only join sources; no contable endpoint mutates a comercial table; the saldo loop is derive-at-read |
| `radicado` null causes `totalGastosProceso` drift | Low | Group por_proceso costs by `procesoId` (stable); `radicado` is a display/secondary key only, backfilled into the snapshot when the Proceso is later filed |

## Rollback Plan
The schema change is additive and applied with `prisma db push` (no migration history). Rollback is manual and safe because no existing table's columns are altered (the back-relation fields are virtual in Prisma and produce no column changes): `DROP TABLE` the 8 new tables in FK-dependency order (`cartera`, `ingresos`, `caja_menor_movimientos`, `cajas_menores`, `egresos`, `nominas`, `servicios_fijos`, `cuentas_bancarias`) and `DROP TYPE` the 17 new enums (do NOT drop `ModalidadCobro` — it is owned by comercial) — or `git revert` the schema and re-run `prisma db push`, which drops the now-absent tables (verify on a non-prod copy first, as `db push` can warn about data loss). Remove the `contable` module/service/router, unmount `/contable` from `app.ts`, and revert the `CONTABLE` permiso/RBAC array added to `seed-foundations.ts` (idempotent upserts; re-seeding is safe). Because every new gate is mounted on new `/contable/*` endpoints only and contable never writes into comercial, removal leaves all current behavior intact. Re-run `pnpm generate`.
